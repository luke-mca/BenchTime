## ADR001 Use JSON web tokens(JWT) to handle authentication. 

Status: Accepted

## Context:
BenchTime must identify the user(as a member or manager) on every API request to understand what 
endpoints they can access(see FR-3). For example, a user that is a member must only be able to get 
their own labs and we must guarantee that this authentication cannot be forged by the client. 

## Decision:
BenchTime will use stateless JWTs for user authentication. requireAuth(found in middleware/auth.js) will verify the user's access cookie and sets the req.user = {id, role}. This means that the JWTs will act as the only source of the user identity in the server and no endpoint exposed by the serve will accept a user id/password as a parameter. The server will also not store any state for the user since JWTs are stateless. 

## Alternatives Considered
### Server-side sessions: 
Rejected for now but could be revisited at a later milesone. This would require 
a session store that has not been created and would further complicate the database. A server-side 
session could also introduce latency(due to extra database queries). JWTs were considered a better
fit for the MVP as they are easier to implement. 

### Using HTTP Basic Auth: 
Rejected because it could introduce some vulnerabilities if not encrypted properly and only allows
for credentials on each request. The issue here is that the server also requires a role to be associated with each set of credentials so it can properly identify the user. It is also better if the user can send their unique id on every request instead of their username/password. 

## Consequences For BenchTime
### Positives: 
- The API does not require any states which kees the database simply and reduces latency from extra query operations. 
- The user role can only come from a signed token which makes certain queries, like those done to request the labs associated with a certain manager, easier to handle as they do not need to perform their own authentication or role identification. 

### Negatives: 
- The JWTs are signed but not encrypted. This means that anyone with the token can see the payload. This also means that care must be taken to not expose anything besides the user's id and their role. 
- Two secrets must exist in the deployment environement for the JWT tokens(access and refresh, see .env.example). If either of these are chagned, then everyone with those tokens will be signed out.
